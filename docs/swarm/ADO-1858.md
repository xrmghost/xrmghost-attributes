## Scope and changes

### `PluginExecutionConfigAttribute.cs`

Added `public string[]? FilteringAttributes { get; set; }` with XML documentation that fixes
three things normatively:

1. **null == empty array.** Both mean "no filtering attributes"; downstream registrars must map
   both to Dataverse `filteringattributes = null`, never an empty string. Purely additive change,
   backward compatible.
2. **Update-only.** Meaningful only for the `Update` message; downstream registrars must ignore
   the property for any other message declared on the same configuration. The attribute itself
   performs no message-dependent validation — it is a passive carrier.
3. **Canonical serialization** (6-step ordered rule): trim + drop blanks, lowercase invariant,
   de-duplicate, sort ordinal, comma-join without spaces, emit `null` when the result is empty.
   Stated as mandatory for reflection/Mono.Cecil consumers, because applying the same canonical
   form on both read and write sides is what makes the "step already up to date?" comparison
   order-insensitive and idempotent.

The property preserves source order, casing, and duplicates verbatim. No constructor change, no
validation added — the constructor signature and existing behaviour are untouched.

### `XrmGhost.Attributes.Tests/AttributeTests.cs`

Two test groups added (24 tests total in the project, up from 14):

- `PluginExecutionConfigAttributeTests` (extended): default `null`, empty array accepted, source
  order/casing preserved, duplicates preserved, and mixed-message declaration (`Create` + `Update`)
  storing the value as declared.
- `PluginExecutionConfigFilteringAttributesMetadataTests` (new): reflection-level assertions over
  attributes actually applied to nested test classes, i.e. the shape baked into assembly metadata,
  which is what downstream reflection/Cecil consumers really read. Covers undeclared → `null`,

  distinctly from null, which is exactly why the null/empty equivalence has to be stated in the
  contract rather than assumed from the metadata), order/casing preservation, and a two-attribute
  mixed-message class where only the Update configuration carries filtering attributes.

## Residual risks

- **Consumer canonicalization drift.** If `xrmghost-dataverse` canonicalizes differently (e.g.
  preserves order, or emits `""` instead of `null` for the empty case), every registration run will
  produce spurious step updates. Mitigated only by documentation — the rule is normative in both the
  XML docs and README, but nothing in this package enforces it. A shared helper method would remove
  the risk entirely and is a candidate follow-up.
- **Empty array vs null at the metadata level.** They round-trip distinctly through assembly
  metadata (asserted in tests). The equivalence is a *contract* obligation on consumers, not a
  property of the encoding — a consumer doing `!= null` instead of a length check will misbehave on
  `new string[0]`.
- **Version placement in CHANGELOG.** `publish.yml` takes the version from the first `[x.y.z]`
  match. Any future entry inserted above `1.1.0` without a version bump would publish the wrong
  version. Verified correct here by running the extraction expression.
- **Docs gap.** `docs.xrmghost.tech/attributes/` will not mention `FilteringAttributes` until a
  separate `xrmghost-docs` task lands.
